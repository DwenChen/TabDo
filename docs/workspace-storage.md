# 项目空间管理规范

本文约束 TabDo 工作区内开发产物的生成、保留与清理，与[维护流程](maintenance.md)、[开发指南](development.md)和[数据备份与迁移](backup-and-migration.md)共同使用。目标是让临时产物随任务结束回收，避免每轮预览、构建和诊断继续积累完整程序副本。

## 每轮任务的责任

开始生成大文件前，查看 Git 状态，确认已有未提交改动、正在使用的程序及其他任务的资料。默认通过 context-mode 分析目录占用；不跟随目录链接、不跨工作区扫描或清理。

每轮结束必须处理本轮生成且已消费的程序暂存、下载解包目录、诊断副本和一次性脚本；已有材料只有在确认来源、消费者及保留要求后才进入清理清单。未完成任务、唯一源码副本及用途不明的文件继续保留，不能因位于忽略目录就推断可删。

维护记录写明本轮新增、清理和仍保留的大文件类别、逻辑大小、保留原因及验证结果。纯仓库文档任务没有新增大文件时记录这一事实，无需重复扫描整个依赖树，更不能为了文档修改重新构建、同步预览并产生回退副本。

以下为人工复核阈值，不是自动删除授权或清空目录的硬上限：

- 单轮可重建材料净增长达到 500 MiB，必须在交付前核对新增来源并清理已完成的暂存。
- `.artifacts/` 总量达到 5 GiB，或仍存在多轮完整程序暂存，必须按下表分类盘点，清理可重建材料，并说明受保护证据、工具链等剩余占用。
- 即使未达到阈值，每次预览同步后也必须完成程序暂存及回退副本的收尾，不能等下一次集中清理。

持续增长来自持久资料或独有证据时，保留资料并报告原因；不为达到阈值删除资料。GiB/MiB 按 1024 进位，GB/MB 按 1000 进位；文件逻辑大小不冒充实测磁盘可用空间增量，pnpm 硬链接也可能使两者不同。

## 分类与保留规则

| 类别和位置 | 默认保留与清理要求 |
| ---------- | ------------------ |
| 源码、用户及其他任务未提交改动、Git 历史、资源来源与许可 | 完整保留。不通过恢复旧版本、`git clean -fdx` 或清空未跟踪文件腾空间。 |
| `.local/portable-preview/`、源码预览资料 | 保留当前程序与全部持久资料，不作为历史备份处理。 |
| `.artifacts/backups/preview-sync/update-*/app`、`new-resources` | 成功切换并核验当前预览后，清理已消费的程序暂存；不保留每轮完整解包树。 |
| 同目录的 `previous-resources` | 默认保留最近一次成功同步的完整程序回退副本；新回退副本及当前程序均核验通过后，清理更旧的程序回退载荷。 |
| 同目录的 `preservation.json`、核验日志及清理收据 | 保留小型审计记录。历史记录中的已删除载荷路径只代表当时事实，不再代表现存恢复点。 |
| 其他旧 exe、ASAR、完整解包程序副本 | 确认当前程序可用、已有保留回退且没有排障消费者后清理，不按每次任务永久保留一份。 |
| `.artifacts/downloads/` | 默认只保留当前使用版本的原始发行文件及核验记录；旧版安装包、压缩包和对应重复解包目录在用途结束后清理。 |
| `.artifacts/toolchains/`、`.artifacts/native/` | 保留实际使用的已安装工具链、构建来源和许可；成功安装后的 CAB/MSI/VSIX 下载缓存及可重建中间文件按需清理，不顺带删除工具链。 |
| `.artifacts/work/`、上游参考或任务工作目录 | 已完成任务的一次性脚本、已合入的副本按明确清单清理；先确认独有修改已保留，日志和原始证据另按下文处理。 |
| `.artifacts/runs/` | 保留自动归档的命令、日志、状态、失败证据、截图及 trace，不按运行次数或文件年龄自动淘汰。 |
| `test-results/playwright/`、游离测试输出 | 确认原始自动归档完整可读后，才清理重复副本；未归档或内容不同的文件保留。 |
| `out/`、内置插件 `dist/` | 日常保留当前一套可用产物，避免重复重建或保存多个完整版本；专项空间清理可按可重建产物处理，但不能破坏当前交付资源。 |
| `node_modules/`、pnpm 依赖与开发缓存 | 保留开发依赖及原生可执行文件，按需清理明确的 Vite/ESLint 缓存；不在日常收尾中删除整份依赖或裁剪全局 pnpm store。 |

已登记的版本比较、故障分析等任务可以临时多保留副本，但必须写明用途、所属任务与清理时机；不能仅写“以后可能有用”。不要为执行空间清理新建整份程序或资料备份。

## 预览同步后的收尾

1. 使用既有 `pnpm preview:sync` 更新程序资源，保留 `data`、`legacy` 和已安装插件；同步期间保留旧程序以支持失败回滚。
2. `pnpm test:preview:resources` 通过，并确认本次资料保留核验成功后，将本次 `previous-resources` 确定为保留回退副本。
3. 只清理本次已消费的 `app`、`new-resources` 和更旧的程序回退载荷；保留本次回退、全部 `preservation.json` 及必要核验日志。临时清单不得指向当前预览资源或资料目录。
4. 同步失败时先恢复并核验当前程序，保留失败诊断与唯一可恢复副本；恢复完成前不得按“只留一份”规则删除恢复所需材料。诊断结束后再清理失效的大体积程序暂存。

当前 `preview:sync` 会生成暂存和回退载荷，`test:preview:resources` 只负责核验；两者都不会按本文自动淘汰历史副本。执行者必须同轮完成上述收尾，不能把运行同步或维护命令写作已自动清理。

## 资料与证据保护

清理始终排除配置、LMDB 等数据库、剪贴板历史、收藏、已安装插件、插件资料、浏览器会话和用户创作内容。资料备份与纯程序回退载荷分别判断；含资料的备份不能因名称为 `backup` 或超过保留数量而删除。

缓存清理必须确认具体目录为可重建缓存，并在对应程序退出后执行；不强制结束用户程序，不停止宿主全局剪贴板采集。Cookies、Local/Session Storage、IndexedDB、浏览器分区及名称含 `temp` 的未知目录均不能整体当作缓存清空。

原始测试归档、发布核验收据及被维护记录引用的独有证据不按年龄静默删除。体积过大时先报告其占用；需要压缩、外移或设置保留期限时，明确选择范围、归档位置和恢复办法，验证归档可读并记录新位置后才处理原副本。不得把历史失败记录改写为成功，也不能只保留摘要代替唯一原始证据。

## 安全清理与验收

清理前形成明确清单，逐项记录相对路径、类别、保留理由、文件数及逻辑大小；确认目标未被 Git 跟踪，不与当前程序、持久资料、其他活跃任务或保留回退重叠。

递归删除或移动前校验最终绝对路径确实位于本工作区，检查祖先和子项的 ReparsePoint/符号链接；禁止从宽泛的通配符、目录名或 `.gitignore` 自动生成删除许可。在 Windows 中使用同一 PowerShell 的原生 `Remove-Item`/`Move-Item` 与 `-LiteralPath`，不跨 shell 拼装删除命令。遇到占用、链接、范围不明或读写失败时保留该项并报告，不能升级为更宽范围的强制删除。

清理后的验收包括：

- 核对计划目标是否已删除，记录成功、跳过、失败及实际清理量。
- 对照 Git 状态和受保护文件的路径、大小、修改时间，确认既有改动、当前资料及必要程序仍在。仅对有必要确认内容相同的具体文件进行内容比对，不反复哈希整个仓库、依赖或资料树；数据迁移、恢复与发行核验继续遵守各自必要校验要求。
- 涉及预览周边程序载荷时运行 `pnpm test:preview:resources`；源码、窗口与行为变更另按受影响范围测试，不为纯空间清理重复构建程序。
- 更新当轮历史记录，执行 `pnpm docs:check`、`pnpm maintain`、`pnpm maintain:check` 与 `git diff --check`。`maintain` 负责整理和索引维护，不代替空间清理或留存复核。

清单、结果及必要小型审计文件放入 `.artifacts/cleanup-日期/`；清理完成后移除本轮一次性扫描/删除脚本，长期复用的工具经审阅后进入 `scripts/`。不得把私有资料内容、完整备份、日志或下载包留在根目录、纳入提交或发布。
